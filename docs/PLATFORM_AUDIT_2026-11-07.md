## Changes implemented in this increment

### Student exam answer persistence

- Every supported editable response now enters the existing per-attempt serial queue immediately; the queue writes the latest snapshot synchronously to the existing tab-scoped `sessionStorage` and then debounces network flush by 450 ms. An explicit Save action and connectivity restoration can flush earlier.
- Autosave covers single-choice, multiple-select, short/open text, numeric, ordering and matching responses. Newer unsent values replace older unsent values for a question; the serial queue keeps requests ordered inside the tab. A blank numeric response is scored as an unanswered zero-mark answer instead of raising a grading-payload error.
- Current question index is saved/restored within the same tab session. The exam surface now reports browser online/offline state and distinguishes local waiting answers from server-confirmed saves. The existing server deadline remains authoritative; server-side save rejects closed/expired attempts.
- No new answer key or unnecessary personal information is put into local recovery storage. Candidate answers are still stored in plaintext sessionStorage; this is not a secure vault. A tab close, storage denial, XSS, shared device, multiple tabs, lost response, deadline race or server-side out-of-order request may still require invigilator recovery. An offline submit is not represented as server submission.

### Exam bundle loading

- Moved LiveKit room UI, SDK hooks and styles into a dynamically loaded `ProctoredExamRoom` component. Non-proctored examination sessions no longer need to load the LiveKit UI chunk.
- Next production-build route report for `/take-exam/[attemptId]`: first-load JavaScript fell from **408 kB** to **229 kB** (−179 kB, **43.9%**). Shared initial JS remains 133 kB. The proctored case will load the separated LiveKit chunk when needed; the total proctored-session payload was not claimed to shrink by the same amount.

## Security, data integrity and external dependencies

- A follow-up live policy review found `platform_settings.ps_select` allowed every authenticated user to read every settings row. Metadata showed rows for the Super Admin identity and internal operational/proctoring settings. **Provisional severity: medium confidentiality risk** because the policy exposed protected settings to any signed-in account; no values were queried and no prior read/exfiltration was demonstrated. Migration `20261107050302` replaced the broad rule with access limited to the billing instructions needed by customer workspaces, or Super Admin access. The service-role path used for backend feature/config reads remains available. The deployed policy predicate was re-read from `pg_policies` after applying the migration.
- The platform-settings policy change passed five isolated PGlite checks: normal authenticated user sees only payment instructions and cannot write; Super Admin retains all rows and writes; anonymous users see none; service role retains backend access. This models policy behavior but is not a direct live authenticated-session test.
- A second review found `support_tickets.sup_insert` allowed arbitrary direct inserts by anonymous/authenticated REST clients (`WITH CHECK (true)`). The public contact form writes through a server action using the service role, so this table policy was unnecessary for the app's path. Migration `20261107050502` removed direct anon/auth insert access; four isolated PGlite checks confirm direct clients are blocked while the server-role insert and Super Admin review/update path remain available. This is a **provisional medium integrity/abuse risk**; no abuse or customer data change was observed. The public contact server action itself still needs rate limiting/abuse monitoring.
- A further review reproduced a **high-severity tenant privilege-escalation path**: under the old `mem_update` policy, an authenticated tenant admin could directly update their membership role to `owner`. The separate `org_delete` policy allows owners to delete an organization, and live FK metadata shows organization deletion cascades into tenant content tables. No production mutation/attack was attempted. Migration `20261107050948` now prevents non-Super Admin membership INSERT/UPDATE/DELETE from assigning, changing or removing `owner` rows; the explicit Super Admin/service-role ownership transfer path remains. Eight isolated PGlite checks reproduce the old self-promotion and verify the hardened policies plus ordinary member management. The production policy predicates were re-read after migration.
- All three production policy migrations are recorded; DB, Auth, REST and Storage remained healthy. The focused role fixtures do not replace a live authenticated two-tenant session matrix, which remains outstanding.
- Existing server-side authorization, candidate-token checks, expiry checks and RLS were not weakened. Prior audit evidence documents selected RLS and tenant-isolation tests, but broad security acceptance remains incomplete.
- High-priority remaining concerns from prior code/production audits: exam answer write/submit/marking operations are not fully atomic or versioned; candidate and tab credentials/local answer storage need continued threat-model review; shared-link identity does not prove person-level identity; file storage bucket/path access requires hardening review; rate limiting and historical question snapshots remain; spreadsheet parsing has unresolved advisories; full multi-tenant billing/role matrix has not been penetration-tested.
- Realtime repeatedly reports a healthy service but `db_connected: false` and `replication_connected: false`; do not rely on subscription-driven updates until Supabase operations resolves or explains this status.
- AI provider, LMS/SIS integration and native OS lockdown require external provider/service/policy work. No new provider or duplicate service was introduced.
